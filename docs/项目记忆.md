# 项目记忆

> 本文件保存需要长期沿用的项目决策，不记录临时聊天内容。若后续讨论产生新决定，应更新本文件并在 `CHANGELOG.md` 留下记录。

## 项目定位

- 书名：《RGB Value Analysis》
- 副标题：重新理解 Bitcoin 应用层
- 唯一主线：RGB 如何一步一步把 Bitcoin 从“价值储存网络”变成“价值流通网络”。
- 目标读者：普通 Web3 用户，而非协议工程师或通用 Crypto 项目研究者。
- 内容范围：只讨论 RGB、Bitcoin、Lightning、UTXO、UTEXO、Mint、Wallet、USDT、DEX、LP、RGB-LSP、BTCFi、Payment、RWA、AI 和 Game 等与 RGB 主线直接相关的内容。
- 不做：通用 Crypto 项目分析；不展开 Solana、Sui、Monad 等无助于解释 RGB 设计的比较。

## 写作原则

每篇只回答一个问题，并按以下顺序组织：为什么需要它 → 它解决什么问题 → 它创造什么技术/生态/流动性/应用价值 → 未来还能演化成什么。

技术细节只是回答问题的工具。每篇必须同时写清价值、代价、风险和待验证项；协议事实、产品已支持、推断和愿景必须分开标记。

## 发布节奏

- 正式承诺采用 **35–40 天完成 20 篇**，不采用 30 天硬冲作为默认计划。
- 前 8 篇是全书地基，平均每 1–1.5 天完成一篇。
- 后 12 篇平均每 2 天完成一篇，给 BTCFi、全球支付和未来应用留出更充足的核验时间。
- 正式连载前至少准备 4 篇存稿，避免因状态波动断更。
- “30 天完成”只作为挑战目标，不作为质量承诺。

## 单篇标准

- 建议长度：1,800–2,800 字。
- 每篇至少包含：一个明确问题、一张核心流程图或关系图、一条一手资料、一个限制/风险段落、一个下一篇预告。
- 发布格式：`《RGB Value Analysis》第 XX 篇｜问题标题`，开头标注 `第 X/20 篇`，结尾固定为“下一篇预告 + 一个简单提问”。
- 配图提前制作 3–4 套模板：问题图、流程图、四类价值图、边界/风险图。

## 内容与发布的双层结构

- GitHub：保存完整书稿、证据、参考资料、流程图说明、版本记录和勘误。
- 社交平台：发布 1,800–2,800 字的阅读版本，强调场景和可读性，不必与 GitHub 全文逐字相同。
- 社交平台版本必须链接回 GitHub 对应章节；GitHub 版本必须保留完整事实边界。

## 每篇发布前检查

- 是否只回答一个问题？
- 普通 Web3 用户能否读懂开场、机制和结论？
- 是否讲清技术、生态、流动性和应用四类价值？
- 是否有一手资料、核验日期和状态标签？
- 是否写出了限制、风险和失败模式？
- 是否删除了与 RGB 主线无关的通用 Crypto 内容？
- 是否自然引出下一篇？
